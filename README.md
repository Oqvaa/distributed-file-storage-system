# Distributed File Storage System (DFSS)

A Java 21 and Spring Boot file-storage prototype that splits uploaded files into chunks, stores two copies of each chunk across logical storage nodes, and reconstructs files with replica fallback.

## Features

- Multipart upload with configurable request/file limits
- Configurable chunk size (1 MiB by default)
- Round-robin primary placement and replica placement on the next node
- PostgreSQL metadata for files, chunks, and storage nodes
- Unique file identifiers generated by a PostgreSQL sequence
- Chunk metadata persisted in batches
- Streaming downloads that do not create a second full-size file on disk
- Replica fallback when a chunk copy is missing or unreadable
- File deletion and best-effort cleanup after failed uploads
- Environment-based database credentials and storage paths

## Architecture

```text
                         Client
                           |
                      REST API
                           |
                     Spring Boot API
                      /         \
             PostgreSQL       Chunk service
             metadata              |
                            +-------+-------+
                            |       |       |
                          Node1   Node2   Node3
                            |       |       |
                            +-- chunk replicas --+
```

**Deployment note:** Node1, Node2, and Node3 are currently logical node directories on the filesystem configured by `DFSS_NODES_PATH`. This demonstrates chunk placement and replica selection, but it is not yet a multi-machine cluster. To distribute data across machines, configure separate node agents or mount independent remote volumes and add node health checks/remote I/O.

## Upload flow

1. Receive the multipart upload and write it to a uniquely named temporary file.
2. Create a file metadata row and obtain its database-generated ID.
3. Stream the temporary file in configurable chunks.
4. Write each chunk to a primary node directory and the next node as its replica.
5. Batch-save both chunk locations in PostgreSQL.
6. Update the file's chunk count and remove the temporary upload.

## Download flow

1. Fetch the file and its chunk metadata from PostgreSQL.
2. Process chunks in part-number order.
3. Read the first available copy; try the other copy when one is missing or unreadable.
4. Stream reconstructed bytes directly to the HTTP response.

The download buffers at most one chunk at a time before writing it to the response. This lets the system retry a replica after a read failure without appending a partial chunk to the response.

| Spring Data JPA | Metadata persistence |

| Maven | Build |
| Java NIO | Chunk storage and streaming |

## REST API

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/files/upload` | Upload a file (multipart field: `file`) |
| GET | `/api/files` | List file metadata |
| GET | `/api/files/{id}` | Get one file |
| GET | `/api/files/download/{id}` | Stream a reconstructed file |
| DELETE | `/api/files/{id}` | Delete a file and its chunk copies |
| GET | `/api/files/nodes` | List configured storage-node records |

## Run locally

Requirements: Java 21, Maven, and PostgreSQL.

Create a database named `dfss`, then run the application from the `DFSS` directory:

```bash
cd DFSS
export DB_URL=jdbc:postgresql://localhost:5432/dfss
export DB_USERNAME=postgres
export DB_PASSWORD='your-local-password'
mvn spring-boot:run
```

The application uses these defaults when environment variables are omitted:

| Variable | Default | Purpose |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/dfss` | JDBC URL |
| `DB_USERNAME` | `postgres` | Database user |
| `DB_PASSWORD` | empty | Database password; set this outside source control |
| `DFSS_OUTPUT_PATH` | `./Storage/Output/` | Temporary upload directory |
| `DFSS_NODES_PATH` | `./Storage/Node` | Parent directory for node folders |
| `DFSS_TOTAL_NODES` | `3` | Logical storage-node count (minimum 2) |
| `DFSS_CHUNK_SIZE` | `1048576` | Chunk size in bytes |
| `MAX_FILE_SIZE` | `100MB` | Maximum uploaded file size |
| `MAX_REQUEST_SIZE` | `100MB` | Maximum multipart request size |
| `SHOW_SQL` | `false` | Enable SQL logging |

New local storage data and `.env` files are ignored by Git. Older chunk files already tracked in the repository remain tracked; to stop tracking them while keeping local copies, review and run `git rm -r --cached DFSS/Storage` from the repository root. Do not commit database passwords or generated file chunks. Because a database password was previously committed in source configuration, rotate that credential; removing it from the latest version does not erase it from Git history.

## Current limitations / next steps

- Logical node directories currently share one host filesystem; remote node communication is not implemented.
- Node health is stored as metadata but is not currently updated by heartbeat checks.
- Checksums and chunk-level integrity verification should be added before treating replicas as production-grade.
- Authentication, authorization, quotas, and per-user ownership are not yet implemented.
- For production, replace Hibernate schema auto-update with versioned database migrations and define a retention policy for temporary/download artifacts.
